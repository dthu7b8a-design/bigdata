# 项目技术档案与交流准备

本文用于复习实际工程、解释设计取舍和准备技术交流。实现事实以当前源码为准，执行结论以 [验证记录](VALIDATION.md) 为准。未来研究建议单独标明，不包装为已经实现的创新。

## 1. 整体设计与调用关系

主链是“课程 CSV → Spark 离线处理 → ADS 快照 → 显式 MySQL 发布 → Flask → Vue”。离线训练不在 HTTP 请求中执行，浏览器刷新只读已发布版本。可选旁路用 WebHDFS 存储、回读原始 CSV 后在本地复算，不通过 YARN 调度。

    participant V as Vue
    P->>D: 留存原件、Parquet、质量记录

## 2. 数据处理原理

### 2.1 来源与可追溯性

pipeline 先逐字节复制三 CSV 到本批次 ODS，并计算 SHA-256。输入不原地修正；源摘要进入 meta。结果与来源可以对应，拒绝记录仍能定位。摘要证明文件一致，不证明采集事实真实或数据有公开许可。

### 2.2 清洗、关联与守恒

会话先全字段去重，修剪文本、解析类型和时间；冲突 sessionId 以及无效时间/数值进入 rejected。年份0014/0015按内部星期、小时和时长一致性解释为2014/2015。仅电量>0、时长(0,24]小时等规则通过的会话参与有效总体。

clean_stations 对设备数和键校验，补显式缺失标签并保留标记；pipeline 检查唯一站点关联，避免 join 放大行数。会话、站点、电池分别检查有效数+拒绝数守恒；规则计数可能重叠，不能把各规则命中数相加当拒绝总数。

当前基线3,395条会话中有效3,339，隔离56；十维均应与19,719.59kWh对应。免费订单不等于零电量；费用使用Decimal相关处理，币种未知，不加人民币符号。

### 2.3 统计与展示契约

十维是日期、小时、星期、站点、位置、设施、平台、车辆标记、用户、时长分桶。交叉比较是站点×小时、平台×工作日类型；另有energy_duration散点明细。

数据库要求12个核心图表数组，允许合法扩展数组，因而散点数组可额外存储。quality保存规则、拒绝数、教学时段、IQR阈值、对账结果及限制。IQR只是候选异常提示，不自动把真实长尾删除。

### 2.4 电池与时段边界

clean_telemetry按电流、SOC、温度、能量/容量和电压校验，保留原值及逐条原因。所有1,594条负电流按课程规则隔离，项目不据此声称测量物理错误已被外部确认。record_time精度不足，不重建连续曲线；不将未知单位字段用于主要电量或模型。

峰平谷是教学小时分组，只按起止小时分类，不拆分跨时段费用，不能解释为实际电价分析。

## 3. 预测实现与评估

forecast构造完整日历，未记录日期置零，并明确零表示文件无记录，未证实真实需求为零。六特征依次是lag1、lag7、mean7、weekday_n、month、trend；mean7窗口只覆盖此前7天，lag特征不包含当前目标。

按时间顺序70%/15%/其余划分，基线有效特征314天，对应219/47/48。候选包括：

- 同星期历史基线：预测等于lag7。
- 线性回归：regParam=0.1、elasticNetParam=0、maxIter=60。
- 随机森林：32棵树、maxDepth=5、seed=20260914。

用验证集RMSE选择；测试集只做最终报告，不参与选型。ML预测截断为非负。保存所有MAE/RMSE/R²，不能挑有利指标宣传。线性回归测试RMSE约45.147优于基线47.650，但MAE约33.771劣于基线32.622；RF明显更差。

测试期特征使用此前已观测真实日值，是滚动单步评估，不是一次性多步预测。之后两种ML模型在全部可用日期重训，用于历史次日2015-10-05的约165.37kWh投影。保存的是全量重训模型，不是训练子集上评估用的原模型；两者用途不同。

模型文件只存回归模型参数，不存整个CSV清洗和VectorAssembler流水线；独立推理须使用相同特征顺序及口径。跨平台浮点可有差异，不能承诺模型文件逐字节一致。

## 4. 数据库与API设计

### 4.1 版本化发布

db.initialize_schema建立三张InnoDB表：

- dashboard_runs：UUID、导入时间、来源摘要、meta/kpis/quality/model JSON。
- dashboard_charts：以run_id和chart_name保存各数组。
- dashboard_active：singleton=1对应活动UUID。

import_snapshot在接触数据库前验证顶层、必需数组、合法图表名和非有限数。初始化DDL独立完成；随后版本、图表、活动指针在同一事务提交，异常rollback，旧活动版本继续可读。历史记录保留，不做未请求的数据淘汰。

每次导入产生新UUID；source_sha256是规范序列化后的快照摘要，不等于原JSON文件字节摘要。源CSV摘要另存在meta.source_sha256。

### 4.2 一致性读取与错误行为

db.connect设置REPEATABLE READ；load_snapshot在同一事务读活动版本及图表，避免一次请求混入不同版本。它不是跨多个HTTP请求的全局锁定，也不能自动消除所有并发写入问题。

create_app提供health/dashboard/quality/model。health检查连接和活动版本，但完整快照仍由dashboard校验。结果接口拒绝start/end或未知查询参数，503区分库不可用、未导入、快照损坏。静态路由检查解析后的根目录与隐藏路径，提供SPA回退但不把未知API当页面。

Flask只监听localhost，未配置生产鉴权、TLS、WSGI、限流。不要将本地演示服务器直接描述为可公网部署的完整生产服务。

## 5. 前端与工程运行

App.vue管理加载、成功、失败和空数据状态；失败不显示随机/缓存KPI。ChartPanel封装ECharts生命周期，charts.js负责统计配置，style.css负责响应式布局。DataV用于视觉组件，不承担数据分析或数据库职责。

runtime尊重现有JAVA_HOME等配置；Windows可指定ASCII Python环境避免.cmd编码问题。环境参数化解决机器绑定，不改变清洗或模型行为。MySQL bootstrap固定专用3307，生成本地随机凭据，不接管原3306。

HDFS sync上传后重新下载比对SHA，manifest与下载文件共同构成证据。pipeline回读三CSV，验证来源后调用同一Spark流程，将KPI/图表/质量/模型结果按语义比较，忽略批次和生成时间，不将上传日志冒充重新计算。

## 6. 已遇到的真实问题与处理

| 问题 | 原因与处理 | 仍有边界 |
|---|---|---|
| 新旧看板数字不一致 | 早期统计原始会话，最终按课程规则统计有效订单；核对run和源摘要，截图区分版本 | 历史图片不能冒充新口径 |
| 本机能读模型，Git克隆不完整 | 无根锚点data/忽略了模型参数子目录；保留完整参考模型、逐文件校验 | 不随意删metadata/CRC证据 |
| 中文路径启动Spark失败 | Windows .cmd和解释器路径编码；ASCII环境并尊重显式配置 | 不同系统需分别验证 |
| 导入失败可能半更新 | 多表发布需原子切换；事务+活动指针，故障注入验证回滚 | schema DDL不等于业务事务 |
| 指标与图表可能读到不同版本 | 同一读取事务取得快照 | 多HTTP请求不共享事务 |
| 电池数据无法画可信曲线 | 负电流规则与时间精度限制；保留原件、隔离并说明 | 不能替代真实传感器数据 |
| HDFS存储被误称分布式计算 | WebHDFS传输，本地Spark计算；文档显式标明local[2] | 没有YARN集群性能结论 |
| 锁定依赖有安全告警 | 固定依赖保留复现性，记录审计；本次不贸然升级 | 锁定不代表安全，升级需独立兼容验证 |

## 8. 面试问题与深入追问

### 1. 为什么用Spark，数据规模是否必须？

- 问题：三千条会话用pandas也能完成，Spark价值在哪里？
- 回答：这是课程指定技术路线，用于练习DataFrame、分层落盘与ML流程；当前规模不证明性能优势，pandas可能更轻量。
- 项目证据：pipeline全流程Spark，runtime默认local[2]，无大规模压测。
- 追问：如何设计同口径pandas/Spark耗时、内存与启动成本对照？

### 2. 怎样证明清洗没有偷偷丢数据？

- 问题：3,395为何变成3,339？
- 回答：原件及摘要不改；55条零电量和1条超长会话隔离，守恒检查有效/拒绝/去重。
- 项目证据：session_reasons、pipeline计数断言和test_pipeline_results独立CSV计算。
- 追问：重复与主键冲突同时出现时怎样避免重复计数？

### 3. 年份修正有什么依据？

- 问题：0014为何能改为2014？
- 回答：内部星期、起止小时和时长交叉验证支持该解释，但不是外部采集证明；保留原值、核验失败停止。
- 项目证据：pipeline的created_raw/ended_raw与R02/R04规则。
- 追问：时区、夏令时或跨世纪数据会怎样影响解释？

### 4. join怎样避免统计膨胀？

- 问题：站点有重复键会如何？
- 回答：关联前检查主键唯一；有效站点semi-join筛选，之后检查属性一致，十维对账。
- 项目证据：pipeline站点唯一性、bad_join及聚合守恒断言。
- 追问：若要保留缓慢变化的站点历史版本，需要什么时间键？

### 5. 如何避免时序泄漏？

- 问题：为何不随机切分？
- 回答：未来数据不应进入过去训练；lag和mean窗口仅用过去，按时间切分，用验证集选型。
- 项目证据：forecast的Window、train_end/valid_end及validation_rmse。
- 追问：测试日用了前一测试日真实值，评估任务究竟是什么？

### 6. 线性模型是否全面优于基线？

- 问题：RMSE更低是否代表全面更好？
- 回答：不是，MAE未改善，RF也更差；误差分布和业务损失不同，保留多指标。
- 项目证据：reference/dashboard.json的model.metrics与README结果表。
- 追问：是否改善极端日、是否需要置信区间及多窗口统计检验？

### 7. 缺失日期填零合理吗？

- 问题：无记录能否当作无需求？
- 回答：本项目只解释为给定文件无记录；置零便于日历特征，但可能引入偏差。
- 项目证据：forecast日历left join/fillna及limitations。
- 追问：怎样比较填零、缺失标记与仅完整观测区间？

### 8. MySQL如何保证更新原子性？

- 问题：图表写一半失败怎么办？
- 回答：版本、图表、活动指针同事务，失败回滚，旧指针继续服务；DDL先单独初始化。
- 项目证据：import_snapshot的commit/rollback和失败插入测试。
- 追问：并发发布、幂等导入、历史版本清理应怎样设计？

### 9. REPEATABLE READ解决了什么？

- 问题：为何每次请求不直接查询最新各表？
- 回答：同一事务保证快照与图表来自一致读取视图，避免请求内数据撕裂。
- 项目证据：db.connect与load_snapshot的两次SELECT。
- 追问：多个HTTP接口的响应仍可能跨版本，怎样支持显式版本查询？

### 10. 为什么拒绝日期筛选？

- 问题：有日期字段，为何不接受start/end？
- 回答：当前存的是全量预聚合快照，任意筛选不能由所有聚合直接准确推出，明确400优于假筛选。
- 项目证据：query_error和DATE_FILTER_UNSUPPORTED测试。
- 追问：若支持筛选，明细存储、预聚合粒度及API缓存如何变化？

### 11. HDFS验证证明了什么？

- 问题：是否已经实现Hadoop分布式训练？
- 回答：证明文件上传回读一致及本地重算可对账；计算master仍为local，不是YARN训练。
- 项目证据：WebHDFS manifest、hdfs_pipeline比较、runtime.master。
- 追问：NameNode能访问但DataNode地址不可达时如何排查？

### 12. 测试通过有何局限？

- 问题：pytest和Playwright绿色是否等于服务都可用？
- 回答：单元mock、Spark、CSV对账、真MySQL、真Flask分别记录；外部未就绪可能skip。
- 项目证据：BIGDATA_MYSQL_INTEGRATION与真实Flask test.skip。
- 追问：怎样让CI对不同测试层设独立准入条件？

### 13. 模型如何交付和独立加载？

- 问题：只有metadata够吗？
- 回答：不足，需data参数与RF树元信息；还需原特征顺序/清洗契约，不能只拿模型类名。
- 项目证据：results/reference/models、SHA256.json与forecast.FEATURES。
- 追问：怎样将VectorAssembler、特征版本和模型注册组合成完整推理制品？

### 14. 项目有哪些实际创新？

- 问题：如何描述价值而不夸大？
- 回答：主要为已有技术的工程应用：来源核对、保留拒绝记录、一致性发布和分层验收；没有新算法或可证实科研首创。
- 项目证据：当前源码、基线对比、失败结果与限制。
- 追问：若开展研究，需要何种新数据、假设、消融和可重复实验？

## 9. 可继续研究的方向

1. **滚动时间验证**：多个时间窗与多随机种子比较基线、线性模型、RF，报告误差分布、置信区间及失效区间；当前仅单次切分。
2. **缺失机制敏感性**：区分真实零需求与缺测，比较填零、缺失标记和观测完整子集；首先补充数据来源证据。
3. **站点异质性与泛化**：在数据量允许时比较全局/站点模型、跨站点留出和时间外推；不能从单历史文件推出当前部署效果。
4. **可解释特征与目标定义**：比较单步/递归多步、节律基线和更简单模型；不引入预测时不可获得的天气等字段。
5. **工程扩展实验**：并发发布一致性、输入契约演进、幂等与可恢复发布、规模扩展；用压测结果支撑架构变化。
6. **数据质量研究**：对年份解释、异常规则、免费订单和教学时段做敏感性/消融，避免将人为规则包装为领域事实。

这些是待设计实验，不是当前实现。研究价值应由问题、可靠数据、对照和结果支撑，不能靠换技术栈或扩大架构图证明。
